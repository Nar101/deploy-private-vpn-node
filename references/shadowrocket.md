# Shadowrocket 接入与验收

## 接管前必须回读

- 确认当前真实客户端、全局路由模式和正在使用的节点，不从历史记录猜测。
- 从运行态确认当前主规则文件和本地 SOCKS 监听；`127.0.0.1:1082` 只是常见示例，不是通用默认值。
- 读取业务分组的真实委托关系。若已有 `AI专用`、`OpenAI专用` 等分组，优先让它们委托统一上层组，不写死具体节点名。
- 新节点使用中性本地名称；公开文档、日志和截图不写入用户真实节点名或订阅信息。

## 安全操作顺序

1. 读取首页当前选择、全局路由模式、节点列表和代理分组。
2. 不切换全局路由、不关闭 VPN、不改变当前节点，除非用户在动作发生前确认。
3. 添加新节点后先做节点级测试。
4. 需要把业务流量迁到新节点时，优先令业务组委托 `PROXY`，再确认 `PROXY` 当前节点。
5. 保存后回读分组 UI，并用本地 SOCKS 请求验证出口 IP。
6. 从 Shadowrocket 运行时日志确认目标域名实际命中预期组。

## 为什么不直接编辑底层文件

Shadowrocket 的可见配置、iCloud 源数据库、运行时 `rule.db` 与隧道缓存不是同一个对象。直接改一个 SQLite 文件可能：

- 改到历史副本而不是当前真相源；
- 被 iCloud 静默回滚；
- 文件已变但运行时缓存仍使用旧规则；
- 破坏规则顺序或数据库完整性。

因此节点和代理分组优先使用 Shadowrocket UI。只有 UI 无法完成且用户明确授权时，才：

1. 确认当前真实生效文件；
2. 备份并记录 SHA-256；
3. 做最小 SQL 修改；
4. 执行 `pragma integrity_check`；
5. 刷新应用与隧道缓存；
6. 从日志和出口 IP 双重验收。

## 延迟判断

Shadowrocket 显示的是一次短连接样本，受 DNS、测试目标、协议握手、运营商国际出口和晚高峰影响。不要用一次 200–400 ms 或一次超时决定节点是否失效。

至少同时观察：

- 连续三次是否能连接；
- 真实网页/API 响应；
- 出口 IP 是否正确；
- 不同网络环境是否都失败；
- 是否存在持续丢包而非单次抖动。
